# dev-workflow 产品需求文档（PRD）

| 项 | 值 |
|---|---|
| 项目名 | dev-workflow |
| 版本 | v1.0 定稿 |
| 状态 | 已确认（用户评审通过，2026-10-17） |
| 日期 | 2026-10-17 |

## 1. 背景与问题

用户以 Trae CN 为主力环境，通过 AI agent 进行项目开发。当前痛点：

1. 开发流程无固定章法，每个项目都即兴推进，质量和完整度不稳定。
2. 任务与进度缺乏统一存档机制，会话结束上下文即丢失。
3. 流程约定若绑定单一 agent，换用其他 agent（Claude Code / Codex 等）即失效。

## 2. 产品定位与用户

**dev-workflow** 是一套管理 agent 开发流程的系统，由三部分组成：**约定（流程规则）+ 模板（文档骨架）+ CLI 脚本（自动化动作）**。它管理一个项目从需求到交付的完整生命周期（6 阶段）。

- 主用户：Rex（项目所有者、需求方、最终验收方），单人使用。
- 执行者：任意 coding agent（当前主力 Trae CN）。agent 通过读取仓库内通用约定文件获得流程指引，不依赖特定 agent 平台的私有功能。

## 3. 产品契约

| 要素 | 定义 |
|---|---|
| 触发 | 用户新建一个被管理的项目，或在现有项目上继续迭代 |
| 核心工作 | 按 6 阶段流转：每个阶段有明确入口条件、动作、产出与完成门槛 |
| 完成条件 | 所有 Task 完成、通过测试与用户验收，项目归档 |
| 信任原则 | **本地文件是唯一事实源；GitHub 是单向镜像存档** |

## 4. 核心对象（唯一定义）

| 对象 | 定义 | 载体 |
|---|---|---|
| 项目 Project | 一个被 workflow 管理的开发项目，独立文件夹 + 独立 GitHub 仓库 | `trae-test/<项目名>/` |
| 阶段 Phase | 项目的生命周期状态，共 6 个（见 §5） | 状态文件 |
| 任务 Task | 最小可交付工作单元；一个 Task 关联至多一个 Issue | `tasks/<id>-<标题>.md` |
| Issue 镜像 | Task 在 GitHub 上的单向副本，仅用于存档与远端可见性 | GitHub Issues |
| 状态文件 | 记录项目当前阶段与全部 Task 状态的机器可读文件 | 仓库内（格式 TBD） |

## 5. 六阶段核心旅程（P0）

```
阶段1 需求/PRD → 阶段2 技术规范 → 阶段3 Demo 验证 → 阶段4 Task/Issue 拆解
     ↑                                                      ↓
     └──── 新需求回流 ←── 阶段6 测试与验收 ←── 阶段5 Agent 执行
```

每个阶段包含：入口条件 → 动作 → 产出 → 完成门槛。**门槛不通过不得进入下一阶段。**

### 阶段 1：初始化与需求（PRD）

- 入口：用户提出新项目想法，或对现有项目提出新一轮需求。
- 动作：agent 将想法拆解为关键决策问题，多轮反问与头脑风暴；提问方式为**逐题 + 选项卡**（见 FR-1）。
- 产出：`docs/prd.md`（按模板，含「已确认决策记录」与 [TBD] 标记）。
- 完成门槛：用户明确确认 PRD。

### 阶段 2：技术文档与规范

- 入口：PRD 已确认。
- 动作：确定技术栈；撰写 `docs/tech-spec.md`；建立通用约定文件体系（AGENTS.md、目录规范、commit 规范、模板库）。
- 产出：技术文档 + 约定文件齐备。
- 完成门槛：用户确认技术方案与规范。

### 阶段 3：Demo 验证

- 入口：技术方案已确认。
- 动作：实现最小闭环 Demo；列出需技术验证的风险点并逐一给出结论。
- 产出：可运行的 Demo + 技术验证结论清单。
- 完成门槛：Demo 跑通、验证点全部有结论，用户确认继续。

### 阶段 4：Task 拆解与 Issue 对接

- 入口：Demo 验证通过。
- 动作：将 PRD 与技术方案拆解为 Task（按模块划分，含验收标准）；运行同步脚本单向创建 GitHub Issues；将 Issue 编号回填至 Task 文件。
- 产出：`tasks/` 全量 Task + 对应 Issue 编号。
- 完成门槛：所有 Task 均有 Issue 编号。

### 阶段 5：Agent 执行与并发

- 入口：Task 已拆解完毕。
- 动作：按 Task 交给 agent 执行，无依赖 Task 可用子代理并发（见 FR-8）；每完成一个 Task 即 commit（中文备注 + 模块前缀 + Issue 号）并推送远端；同步更新 Task 状态与 Issue 状态。
- 产出：已完成代码 + 远端同步的 commit 历史与 Issue 状态。
- 完成门槛：所有 Task 状态为 done 且已推送。

### 阶段 6：测试与迭代闭环

- 入口：全部 Task 完成。
- 动作：agent 测试复查 → 用户视觉/实际体验验收 → 收集反馈；缺陷生成修复 Task，新需求回流至阶段 1 增量更新 PRD。
- 产出：验收结论 + 迭代回流记录。
- 完成门槛：用户验收通过，项目归档；否则循环。

## 6. 功能需求

### FR-1 头脑风暴引导（阶段 1）

- 触发：用户提供项目初始想法。
- 规则：
  1. agent 将需求拆为若干**会实质改变产品形态**的关键决策问题，逐题提问（不一次性抛出全部问题）。
  2. 每题渲染选项卡（2-4 个选项），标注推荐项；用户可点击选择、回复字母，或自由作答。
  3. agent 能自行查证的环境事实（如工具是否安装、账号是否登录）不提问，直接检查并汇报。
- 结果：全部关键决策写入 PRD「已确认决策记录」章节。

### FR-2 PRD 生成（阶段 1）

- 使用 `docs/templates/prd-template.md` 生成 `docs/prd.md`。
- 未知信息标 `[TBD]`；推断性结论标 `[假设]`；禁止编造数据与业务规则。
- PRD 必含：产品契约、核心对象定义、六阶段旅程、功能需求、已确认决策记录、非目标。

### FR-3 通用约定文件体系（阶段 2）

- `AGENTS.md`：任何 agent 进入仓库后的操作手册——6 阶段流程指引、文件地图、规则引用入口。
- `docs/templates/`：PRD、技术文档、Task 模板。
- commit 规范：`<类型>(<模块>): 中文描述 #<Issue号>`；类型 ∈ feat / fix / docs / refactor / test / chore。
- Trae 项目规则文件仅放一行引用指向 `AGENTS.md`，不复制内容。

### FR-4 Demo 验证清单（阶段 3）

- 阶段 2 产出「技术验证清单」（写入技术文档），阶段 3 逐项验证并记录结论（通过/不通过/替代方案）。

### FR-5 Task 模型（阶段 4）

- Task 文件字段：`id`、`标题`、`模块`、`描述`、`验收标准`、`依赖`、`状态`、`Issue 编号`。
- 状态机：`todo → in-progress → review → done`；任意时刻可进入 `blocked`。
- 拆解规则：按模块划分；单个 Task 原则上可由一个 agent 会话独立完成；有依赖关系的 Task 标注依赖 id。

### FR-6 Issue 单向同步脚本（阶段 4 / 5）

- 行为：扫描 `tasks/`，为尚无 Issue 编号的 Task 创建 Issue（标题、正文按模板，正文内含 Task 全字段），将 Issue 编号回填 Task 文件；Task 状态变为 done 时关闭对应 Issue。
- 幂等：以 Task 文件中已回填的 Issue 编号为准去重，重复运行不产生重复 Issue。
- 异常：
  - gh 未登录 / 无网络：明确报错并提示处理方式，不静默失败。
  - 同步中断：可安全重跑。
- 同步方向：仅 本地 → 远端；远端对 Issue 的编辑不回写本地（本地永远为准，不构成一致性冲突）。

### FR-7 commit 与推送规范（阶段 5）

- 每个 Task 完成（进入 review 或 done）即 commit 并 push；commit 必须关联 Issue 号。
- 禁止跳过 hooks、禁止 force push；push 失败需重试或报告，不得静默丢弃。

### FR-8 并发执行（阶段 5）

- 无依赖关系且分属不同模块的 Task 可并行分派给多个 agent / 子代理。
- 并发上限：默认 **3**，可配置；上限变更不影响已分派中的 Task。
- 并发分组原则：同一时间修改同一文件集的 Task 不得并行。
- 每个 agent 开始前必须读取 `AGENTS.md`、`docs/prd.md`、技术文档与所认领 Task 文件。

### FR-9 验收与迭代回流（阶段 6）

- 视觉/体验类产出由用户实际操作验收；agent 提供可访问的运行方式（本地服务或构建产物）。
- 反馈分类处理：
  - 缺陷 → 新建修复 Task（关联原 Issue 或新建 Issue），进入阶段 5。
  - 新需求 → 回到阶段 1，增量更新 PRD 后走后续阶段。

### FR-10 Trae 项目级 Skill 封装（阶段 2 产出，随仓库维护）

- dev-workflow 仓库内包含一个 **Trae 项目级 Skill**：`SKILL.md` + 参考文件（六阶段流程指引、提问规范、CLI 命令用法、阶段门槛定义）。
- Skill 定位为**流程触发器与操作手册**，不复制事实内容；事实源仍为仓库内 `AGENTS.md`、`docs/`、`tasks/` 与状态文件。
- 触发：用户在 Trae 中点名（如「用 dev-workflow 开始新项目 / 继续当前项目」），或请求与 skill 描述语义匹配时自动调用。
- Skill 随 dev-workflow 仓库版本化；其他项目需要使用时，将该 Skill 复制或引用安装到对应项目。

## 7. CLI 脚本功能（产品级）

| 命令 | 行为 |
|---|---|
| `workflow init` | 初始化项目骨架：目录结构、约定文件、模板、git 仓库 |
| `workflow task new` | 按 Task 模板新建任务文件 |
| `workflow task sync` | FR-6 的单向同步 |
| `workflow status` | 终端摘要：项目阶段、Task 完成度、Issue 对应关系 |

> 命令名与实现形态（语言、是否合并为单脚本）由技术文档决定，此处仅约束行为。

## 8. 状态流转汇总

| 对象 | 状态集 | 流转 |
|---|---|---|
| 项目 Phase | 1 需求 → 2 规范 → 3 Demo → 4 拆解 → 5 执行 → 6 验收 | 门槛通过才前进；迭代可从 6 回 1，缺陷从 6 回 5 |
| Task | todo / in-progress / review / done / blocked | 见 FR-5 |
| Issue | open / closed | 跟随 Task：创建即 open，done 即 closed |

## 9. 边界与异常场景

| 场景 | 处理 |
|---|---|
| 中途更换 agent | 新 agent 读 `AGENTS.md` + PRD + 技术文档 + 状态文件即恢复全部上下文 |
| sync 重复运行 | 幂等，不产生重复 Issue |
| Task 字段缺失 | 同步脚本对该 Task 报错跳过并列出缺失字段 |
| 用户长时间未验收 | 项目停留在阶段 6，状态文件如实记录 |
| 验收不通过 | 按 FR-9 回流，不视为失败 |
