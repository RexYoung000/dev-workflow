# 六阶段与执行约定

本文件定义工作流方法；业务需求和技术结论来自消费项目自己的文档，不引用 dev-workflow 源码仓库的 PRD 章节。

| 阶段 | 工作 | 结束条件 |
|---|---|---|
| 1 需求/PRD | 阅读已有资料，逐题确认关键产品决策，维护 docs/prd.md | 用户确认需求 |
| 2 技术规范 | 选择方案，记录规范、约束与验证点，维护 docs/tech-spec.md | 用户确认方案，或已授权按推荐方案实施 |
| 3 Demo | 实现最小闭环，验证关键风险 | 真实运行与验证结论可复核 |
| 4 Task/Issue | 按模块拆任务，含描述、实际验收点和依赖；同步到自己的仓库 | 所有任务合法、Issue 编号齐备 |
| 5 执行 | 完成 Task、验证、维护文档、按项目规范普通提交推送 | Task 全部 done，检查点完成，推送已核对 |
| 6 测试与用户验收 | Agent 复查，提供运行入口、操作步骤和预期结果，交用户体验验收 | 用户明确通过；缺陷回 5，新需求回 1 |

## 阶段机器检查

命令前缀：`python3 .trae/skills/dev-workflow/scripts/workflow.py`。

前进一律阻止异常 Task，包括缺字段、重复 ID、无效 Issue、依赖缺失或成环，以及 done 的未完成验收点。累积检查：

- 进入 ≥2：docs/prd.md 存在且非空。
- 进入 ≥3：docs/tech-spec.md 存在且非空。
- 进入 ≥4：至少一个有效 Task。
- 进入 ≥5：全部 Task 有合法 Issue 编号。
- 进入 ≥6：全部 Task done，验收标准节至少一条实际 checkbox 且全部勾选。

回退免阶段门槛，但不能用回退伪装完成。用户确认、Demo 运行、实际 push 和用户体验不是机器检查项，由主 Agent 核实并记录，不允许只看阶段号宣称完成。

## Task、提交和并发

- 本地 tasks/*.md 为任务状态唯一事实源；todo → in-progress → review → done，可进入 blocked。未知事实和待办不能勾选为完成。
- 现有项目的分支、提交与发布规则优先。无既有规则的独立单人项目采用 main 普通提交，格式 `<type>(<module>): 中文描述 #<Issue号>`，type 为 feat/fix/docs/refactor/test/chore。
- 完成已授权范围、适度验证和文档回写后，执行已获允许的普通 commit/push。禁止强推、跳过 hooks；失败明确报告。发布、生产部署、PR 合并需要单独授权。
- 并发候选必须依赖全部 done、模块不同且文件集不相交；每模块最多一项，max_parallel 默认 3。模块名不能证明共享文件隔离，主 Agent 必须复查。
- Trae 子智能体能力未配置或当前模式不支持时串行。工作流不自动创建 Agent、安装 MCP 或保证并发工具存在。
- 用户提出局部修复时按风险处理，不为小改动机械新建完整文档或重跑六阶段。
