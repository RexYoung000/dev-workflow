# 需求澄清

先读取目标项目现有资料与已确认决定，只问会实质改变产品目标、关键交互、范围、数据处理、成本或授权的问题。能自行查证的环境事实直接检查，不要求用户确认已知事实。

一次只问一个关键问题，通常给出 2–4 个选项，标明推荐项、理由和差异，允许自由回答。当前 Trae 模式提供原生提问工具时使用它；否则用带 A/B/C 的文本列表或表格。普通 Markdown 表格不承诺可点击，不虚构按钮。

已有明确实施授权时，在确定范围内继续；未决选择只暂停依赖该选择的部分。不要因为用户说“OK”就扩展到新需求、外部同步或发布权限。

结论写入本项目 PRD 的决策记录；未知标 [TBD]，推断标 [假设]。不要照搬工作流产品的六阶段定义作为业务产品旅程。

示例：

> Issue 是否作为本地任务的镜像？
> A（推荐）：采用本工作流既定的单向创建/关闭，保留 GitHub 存档。
> B：只做本地规划，暂不走需要 Issue 的完整执行阶段。
> 也可以直接描述需求。若需要双向同步，应作为新范围单独讨论。
